## 3. 阶段划分

### 3.1 阶段 A — PRD 实测与修 bug（先做）

**范围**

- 输入：`docs/prd/globaluser-*.md`（功能页，不含纯 UIUX 推荐文）中的 AC。  
- 页面集合：F01–F14、A01–A13（见 `docs/prd/globaluser.md` §3）。  
- 排除：标 `[待补充]` / `[待运营提供]` 的条款；设计规格中的 Out of scope（移动端、SSO、商城等）；加入审核通过后自动开户等 PRD 已标明待补充项。

**方法（每条可测 AC）**

1. **浏览器**：在运行中的前台（默认 `http://localhost:5173`）与后台（`/admin`）按步骤操作，记录期望 vs 实际。  
2. **数据库**：对写操作查询 `server/data/chuying.db`（或当时 `DATABASE_PATH`），核对相关表行、状态、流水、CMS 已发布列 vs `draft_*` 等与界面一致。  
3. **API（可选）**：仅用于定位或自动化回归，**不能**单独作为 PASS 依据。

**角色与数据（阶段 A）**

- 继续使用现有一键演示三角色（雏英角色用户、管理员、超管）。  
- 破坏性操作（审批、停用、改 CMS）后可重跑 seed / 换库文件以保证可复现。  
- 本阶段**不**批量改「雏鹰→雏英」；遇到错误品牌文案可记一条，留给阶段 B。

**缺陷处理**

- 直修类：改完后对该 AC 做浏览器 + DB 回归。  
- 须确认类：暂停实现，向产品方给出现象、库摘要、2～3 方案与推荐，确认后再改。

**阶段 A 交付物**

- 按页验收清单（AC → 浏览器步骤 → DB 核对要点 → 结果），建议落在 `.agent-scratch/qa/`（或实现计划指定路径）。  
- 已修缺陷列表。  
- `npm test` / `npm run build` 绿。

## 4. 架构与工作流（验收侧）

```text
PRD AC 清单
    │
    ├─► 浏览器操作（主） ──► 记录 UI 结果
    ├─► SQLite 查询（主） ──► 记录落库结果
    └─► API（辅）         ──► 仅辅助定位
            │
            ▼
     PASS | FAIL | 缺口
            │
     FAIL ──► 分类：直修 | 问方案
            │
            ▼
     回归（浏览器 + DB）
```

数据库默认路径：`server/data/chuying.db`（阶段 B 若改文件名则以迁移后路径为准）。使用 `better-sqlite3`；验收查询只读优先，避免手改污染除非为构造夹具。

---

## 5. 错误处理与沟通

- 浏览器无法复现但 API 失败：以浏览器+DB 为准；另开「环境/代理」类笔记。  
- DB 与 UI 不一致：记为缺陷；若涉及规则语义则走「问方案」闸门。  
- Seed 损坏：重建库后重跑相关用例，不把环境问题算产品 FAIL。

---

## 6. 测试策略（本工作自身）

- 阶段 A：以手工浏览器 + SQL 清单为主；合理处可补服务端回归测试，**不替代**浏览器/DB 主证据。  
- 阶段 B：密码登录增加至少一条服务端或冒烟用例（登录成功/失败）；改名后全量 `npm test` + `npm run build`。  
- 不强制引入 Playwright 作为本规格必达项；若实现计划选择自动化浏览器，须仍保留 DB 核对步骤。

---

## 7. 非目标（本规格不做）

- 不实现 PRD 已标待补充的产品能力（只文档化）。  
- 不做移动端适配、SSO、商城。  
- 不在阶段 A 中途大规模改品牌名（避免与验收交叉）。  
- 不将「仅 API 绿」视为功能验收完成。
