# 1.0 阶段产品需求文档（PRD）通用模板

## 1. 产品概述（必选）

### 1.1 产品定位（新增）

- **内容要求**：简洁说明产品核心价值、产品形态、核心功能、解决的核心痛点  
- **颗粒度标准**：≤150 字，无冗余信息（例：PC 端 AI 工具，通过爆款素材聚合+一键二创，解决素材制作效率低的痛点）  
- **撰写规范**：包含「用户 + 场景 + 痛点 + 解决方案」四要素  

**本项目示例口径（可改）**：面向软通智慧雏鹰计划管理者与雏鹰的 Web 端宣传运营站，通过计划展示、加入/活动报名与积分管理，解决计划信息分散、报名与活动运营难统一的问题。

### 1.2 项目背景

- **内容要求**：阐述开发动因（市场需求 / 业务痛点 / 行业趋势）、现有方案不足  
- **颗粒度标准**：≤300 字，数据支撑痛点（例：人工搜集素材需 2 小时/次，规模化生产困难）  
- **撰写规范**：避免空泛，聚焦具体业务场景的实际问题  

### 1.3 目标用户

- **内容要求**：明确用户角色、核心特征、使用场景  
- **颗粒度标准**：角色唯一/明确，特征尽量量化（如「日均制作素材 5+ 条」）  
- **撰写规范**：按「角色名称 + 核心职责 + 使用频率」描述  

**本项目最少角色**：访客｜雏鹰（参与者）｜管理者（运营管理员）。

### 1.4 核心目标

- **内容要求**：量化的产品目标，按优先级排序（参考 SMART 原则）  
- **颗粒度标准**：3–5 条，每条含「指标 + 阈值」（例：AI 生成图片时间 ≤30 秒，替代 80% 人工搜索工作）  
- **撰写规范**：分点列出，标注优先级（如「P0：提效」「P1：赋能」）  
- **缺基线时**：写清指标口径并标 `[待核实]`，不得虚构阈值  

### 1.5 产品边界

- **内容要求**：明确 V1.0 支持的业务范围  
- **颗粒度标准**：具体可界定，避免模糊表述  
- **撰写规范**：按「支持范围 + 不支持范围」分点，与后文 Out of Scope 呼应  

---

## 2. 术语定义（必选）

- **内容要求**：解释文档中专业术语、缩写、特定名词  
- **颗粒度标准**：所有歧义词汇必须定义，无遗漏  
- **撰写规范**：表格形式（术语 + 英文缩写 + 定义），便于快速查阅  

**本项目建议至少定义**：雏鹰、管理者、加入报名、活动报名、积分、流水、后台等。

---

## 3. 功能需求（必选）

### 3.1 功能架构（新增）

- **内容要求**：思维导图形式呈现功能模块层级关系  
- **颗粒度标准**：覆盖所有核心功能，无层级混乱  
- **撰写规范**：自上而下拆解，每个父模块包含 2–5 个子模块  
- **可用形式**：Markdown 树 / mermaid / 附图；逻辑层级优先于操作顺序  

### 3.2 Epic 设计（按功能模块拆分）

#### 格式标准

| 字段 | 内容要求 | 颗粒度标准 |
| --- | --- | --- |
| Epic 编号 | 按「Epic X」命名（X 为连续数字） | 唯一标识 |
| Epic 名称 | 简洁明了，体现核心功能 | ≤15 字 |
| Epic 目标 | 该模块要达成的核心价值 | 与产品核心目标对齐 |
| 核心场景 | 2–3 个关键用户场景 | 覆盖模块 80% 核心使用场景 |
| User Story 列表 | 关联的用户故事编号 | 无遗漏，不重复 |
| 功能边界 | 该模块不包含的功能 | 明确界定，避免需求蔓延 |

#### User Story 设计（每个 Epic 包含 3–10 个）

格式标准：

```markdown
● As a [用户角色]
● I want [具体操作/需求]
● So that [实现价值/解决痛点]
● 验收标准 (AC)：
1. [可测试的具体条件1]
2. [可测试的具体条件2]
...（3-5条，无歧义、可验证）
```

#### 撰写规范

1. 遵循 INVEST 原则：独立、可协商、有价值、可评估、小型、可测试  
2. AC 要求：具体量化（如「加载时间 <2 秒」）、无模糊表述（避免「快速加载」）  
3. 操作流程：≤3 步完成核心功能（符合「傻瓜化」要求）  

### 3.3 功能点辅助约定（本项目补充）

在 Epic / User Story 之外，若需工程拆解，可另附「功能点清单」；命名须为**动词短语**（例：提交加入报名），不得用页面名冒充功能（例：首页、Banner）。

功能层级关系用语（画架构树时）：

| 关系 | 含义 |
| --- | --- |
| 泛化 | B 是 A 的一种形态 |
| 包含 include | 做 A **必然**涉及 B（慎用） |
| 扩展 extend | B 是 A 的可选增强 |
| 平级 | 同一父能力下的并列能力 |

禁止把「先点后点」的操作链路画成唯一 include 链。

## 4. 交互与原型要求（新增，必选）

### 4.1 界面布局原则

- **内容要求**：明确界面核心区域、元素优先级  
- **颗粒度标准**：按「核心区域 → 次要区域 → 辅助区域」划分  
- **撰写规范**：结合产品定位（宣传官网优先叙事与主 CTA；工具后台优先操作效率）  

**本项目前台建议**：首屏突出计划价值与「加入雏鹰 / 查看活动」主路径；后台按「内容 / 报名 / 活动 / 积分 / 用户」分栏。

### 4.2 核心流程流程图

- **内容要求**：包含用户操作流程、数据流转流程  
- **颗粒度标准**：标注关键节点、分支流程、异常处理（如网络异常提示）  
- **撰写规范**：使用标准流程图符号或等价 mermaid，无交叉混乱  

**本项目建议至少画出**：加入报名流程、活动报名流程、积分变动（自动/调账）流程。

### 4.3 关键页面原型

- **内容要求**：提供核心页面线框图  
- **颗粒度标准**：标注元素位置、交互逻辑（如按钮位置、点击后跳转方式）  
- **撰写规范**：明确页面尺寸、适配要求（如优先适配 Chrome；前台需移动端可用）  
- **无视觉稿时**：用文字线框表代替，**不得空节**  

---

## 5. 数据需求（新增，必选）

### 5.1 数据来源

- **内容要求**：明确数据获取方式（爬虫抓取 / 第三方接口 / 用户上传 / 运营录入）、来源平台或系统  
- **颗粒度标准**：标注每个数据源的字段清单  

**本项目常见来源**：运营后台录入（介绍/动态/活动）、用户报名表单、管理员审核与调账、登录身份源 `[待补充]`。

### 5.2 数据更新规则

- **内容要求**：明确更新频率、更新方式（覆盖式 / 增量式）  
- **颗粒度标准**：量化时间、明确数据保留规则  

### 5.3 数据存储要求

- **内容要求**：明确存储内容、存储周期、安全规范  
- **颗粒度标准**：无遗漏关键数据，符合合规要求  

**本项目强调**：报名材料与积分流水须可审计；调账记录保留操作者、时间、前后余额。

---

## 6. 非功能性需求（必选）

### 分类标准（按优先级排序）

| 需求类别 | 内容要求 | 颗粒度标准 |
| --- | --- | --- |
| 平台兼容性 | 明确支持的系统、浏览器、分辨率 | 具体可验证，无模糊表述 |
| 性能指标 | 量化响应时间、并发量等 | 每个指标包含「场景 + 阈值」 |
| 易用性要求 | 操作复杂度、学习成本 | 结合目标用户特征设计 |
| 设计规范 | 输出格式、视觉要求 | 明确输出标准，便于设计落地 |
| 数据安全 | 权限控制、数据加密 | 符合数据安全合规要求 |
| 可扩展性 | 预留扩展、未来迭代方向 | 不影响 V1.0 开发，便于后续迭代 |

**本项目补充优先级语义（可选并用）**：P0 阻断上线；P1 首期必做；P2 首期尽量；P3+ 后续迭代。

---

## 7. 上线标准（新增，必选）

### 7.1 功能验收标准

- **内容要求**：所有 User Story 的 AC 全部通过，核心功能无阻塞性 bug  
- **颗粒度标准**：列出关键功能验收清单  

### 7.2 性能验收标准

- **内容要求**：所有性能指标达标，无明显卡顿、超时问题  
- **颗粒度标准**：按「场景 + 指标 + 测试方法」列出  

### 7.3 合规要求

- **内容要求**：符合版权规范、数据合规、隐私保护  
- **颗粒度标准**：明确合规检查项，无合规风险  

---

## 8. V1.0 暂不实现（Out of Scope）（必选）

- **内容要求**：按功能模块分类，列出暂不开发的功能及原因  
- **颗粒度标准**：明确「不做什么」，避免需求蔓延  
- **撰写规范**：分点列出，标注原因（优先级 / 技术难度 / 场景必要性）  

---

## 9. 附录（可选）

- 参考文档：竞品分析、市场调研、技术规范、团队构想原文等  
- 接口说明：依赖的第三方接口简要说明  
- 其他补充：特殊场景、异常处理、FAQ 等  

**本项目建议附录引用**：

- `docs/ideas/团队构想与思路.md`（原话与待补清单）  
- 对外品牌口径确认记录（雏鹰 / 雏英等）  

---

## 10. 文档元信息与修订（本项目补充）

每份 PRD 文首建议包含：版本 / 日期 / 作者 / 所属迭代 / 规范依据（本文）。  

重大需求变更必须写入**修订记录**，不得静默覆盖旧结论。  

交付前自检：

- [ ] §1–§8 必选章节齐全（附录可按需）  
- [ ] 产品定位含四要素且 ≤150 字  
- [ ] 目标含指标+阈值或已标 `[待核实]`  
- [ ] 术语表覆盖歧义词  
- [ ] 功能架构 + Epic + User Story（含 AC）完整  
- [ ] 交互/原型、数据、非功能、上线标准、Out of Scope 已写  
- [ ] 无臆造数据与空泛验收句  

---

## 11. 与旧版工程详述模板的关系

若评审需要「操作者 / 前置后置 / 主分异常流程 / 输入-验证-执行-反馈」级工程详述，可在对应 User Story 下**追加**该块，但不替代本文 §1–§8 的交付结构。旧版仅列「背景→功能列表→详述」而不含 Epic/AC/Out of Scope/上线标准的写法，**不再作为本项目合格 PRD 标准**。
